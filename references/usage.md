# 进阶使用说明

日常使用只需在 Codex 中发送 `$codex-lm-detector 检测当前模型`。需要手动安装、更新、排障或开发时，再查阅下面对应的部分。

## 聊天用法

在 Codex 聊天中发送下面的示例即可，中文描述不必逐字一致。Codex 会将要求转换成随包脚本支持的参数，无需手动运行命令。

| 用途 | 聊天示例 | 发起模型测试请求 |
| --- | --- | --- |
| 检测当前模型 | `$codex-lm-detector 检测当前模型` | 是，三条挑战 |
| 只检查环境和连接 | `$codex-lm-detector 只做诊断，不发起检测` | 否 |
| 复查历史报告 | `$codex-lm-detector 复查这份历史报告，不重新检测：<报告绝对路径>` | 否 |
| 用文字表格查看历史报告 | `$codex-lm-detector 用文字表格展示这份历史报告，不重新检测：<报告绝对路径>` | 否 |
| 用 JSON 查看历史报告 | `$codex-lm-detector 用JSON展示这份历史报告，不重新检测：<报告绝对路径>` | 否 |
| 增加采样等待时间 | `$codex-lm-detector 检测当前模型，采样等待时限设为300秒` | 是，三条挑战 |
| 本次检测使用文字输出 | `$codex-lm-detector 检测当前模型，用文字表格展示结果` | 是，三条挑战 |
| 本次检测使用 JSON 输出 | `$codex-lm-detector 检测当前模型，结果使用JSON输出` | 是，三条挑战 |
| 指定报告目录 | `$codex-lm-detector 检测当前模型，将报告保存到：<目录绝对路径>` | 是，三条挑战 |

将尖括号占位内容换成实际路径，macOS、Windows 和 Linux 均使用完整的绝对路径。已有报告路径可从检测结果的“查看完整报告”获得。如果仍在同一聊天中，也可以说“把刚才的报告用文字表格展示，不重新检测”。

诊断检查连接、SDK 和参考库，不让模型回答挑战。历史复查重新分析报告中已有的回答，不反映当前模型的新状态。文字和 JSON 只是展示方式：与“检测当前模型”一起使用仍会发出测试请求；与历史报告一起使用则不会。

单次检测固定三条挑战，等待时限默认 180 秒，可设为 5–600 秒，不含连接及会话准备时间。目前不提供批量多模型、自动切换模型、定时检测、携带父聊天历史检测或任意 API 地址检测。

等待时限到达后会停止在途的探针启动等待，不再启动后续探针，并保留已完成的样本。随后还会中断请求、复查配置、关闭进程和保存报告，因此采样等待时限不是整个命令的总耗时上限。

## 手动安装

通常直接让 Codex 安装即可。若需要手动安装，先准备好 Git 和 Node.js 22+，在终端依次执行：

```sh
git clone https://github.com/logan0817/codex-lm-detector.git
cd codex-lm-detector
node install.mjs
```

安装成功后，在目标 Codex 聊天中发送 `$codex-lm-detector 检测当前模型`。若技能未显示，重新打开 Codex。

默认安装目录：

| 系统 | 目录 |
| --- | --- |
| macOS、Linux | `~/.codex/skills/codex-lm-detector` |
| Windows | `%USERPROFILE%\.codex\skills\codex-lm-detector` |

设置了 `CODEX_HOME` 时，使用该目录下的 `skills/codex-lm-detector`。安装不改变登录、模型配置或其他技能，无需 `npm install`。已有目标目录时停止，不覆盖。

## 更新与卸载

更新时：

1. 找到上面的安装目录，将现有 `codex-lm-detector` 文件夹备份并移到 `skills` 目录之外。
2. 使用原来的方式重新安装。手动安装的用户先在克隆的仓库中执行 `git pull --ff-only`，再运行 `node install.mjs`。
3. 确认新版可用后，再删除备份。如果新版无法使用，先将新版目录移出 `skills`，再将备份放回原位置。

卸载时，删除安装目录中的 `codex-lm-detector` 文件夹即可。

从旧名称升级时，先将 `skills/lm-detector` 备份并移出 `skills`，再安装新版，之后使用 `$codex-lm-detector`，避免同时加载两份技能。

更新或卸载技能不会删除检测历史。需要清理历史时，另行删除[报告目录](#报告与隐私)。

## 运行条件

需要 Node.js 22+，以及支持 `thread/read`、`thread/start`、`turn/start` 和 `ephemeral` 临时会话的 Codex 运行时。通过原生 app-server 沿用现有登录或自定义渠道，不读取认证文件提取 Key。

检测应从目标 Codex 聊天内调用。脚本通过 `CODEX_THREAD_ID` 或 `CODEX_SESSION_ID` 定位当前任务；普通系统终端通常没有这些变量，不能直接确定要检测的聊天。

已完成的真实客户端验证如下，均包含三条有效采样、评分和报告保存：

| 环境 | 验证范围 |
| --- | --- |
| macOS 桌面端 | 首版已通过真实检测和结果卡片输出；本次修订尚未在 macOS 上复验 |
| Windows 桌面端 | 沙箱外真实检测、结果卡片输出、自定义及默认报告目录；新版提前申请权限、允许后仅执行一次检测，以及拒绝后停止且不发起模型请求均已实测 |
| Windows CLI（`codex exec`） | 完全访问模式及单独配置运行状态访问权限的隔离 `elevated` 沙箱下的真实检测、自动文字输出、含中文和空格的安装及报告路径 |
| Windows CLI（交互式终端） | 完全访问模式下的真实检测、自动文字输出和报告保存 |

截至 2026-11-09，Windows 已取得上述通过结果，仍存在下述受限沙箱限制；真实检测环境为 Node.js 24.14.1、Codex CLI 0.167.0-alpha.3.2。Node.js 22.22.2 和 24.14.1 的本地回归测试均为 49 项通过、0 项失败、1 项 POSIX 信号测试按平台规则跳过，Windows 终端 Ctrl+C 另行实测通过。另已检查真实连接诊断、报告离线文字／JSON 复查、Git `core.autocrlf=true` 检出及安装；限流、认证失败、额度不足、超时、进程退出、工具调用、配置变化和保存失败使用本地故障注入验证，未对真实渠道制造这些故障。

权限错误处理修订后，Node.js 24.14.1 的最新回归结果为 51 项通过、0 项失败、1 项按上述平台规则跳过，新增覆盖子进程同步／异步权限拒绝，以及会话未加载时停止且不启动采样。

Windows 受限沙箱验证使用已有的 `elevated` 实现和隔离的临时 `CODEX_HOME`，只向 app-server 所需的运行状态文件及临时目录授予写权限；临时目录还需要允许沙箱账号访问。连接诊断、三条有效采样、评分、报告保存和离线复查均通过，同时确认测试工作区可写，原项目文件、原配置及隔离配置不可写。原用户配置未修改，临时配置与测试状态在验证后清理。这证明 Skill 可在具备必要状态访问权限的受限沙箱中运行，不表示默认权限配置无需调整。

本机 Windows 10 的 `unelevated` 沙箱仍存在 `cannot enforce split writable root sets` 或 Node 子进程启动被拒绝（`EPERM`）的限制，当前执行环境不支持 MXC。若 `doctor` 报会话读取、状态库初始化或子进程启动失败，先检查客户端沙箱与 `CODEX_HOME` 权限；不要把此类失败当作检测通过，也不要默认放开整个用户配置目录。沙箱选择和权限配置参见 [Codex 官方 Windows 沙箱说明](https://developers.openai.com/codex/windows/)。macOS CLI 与 Linux 尚未完成真实客户端验证。协议不兼容时停止，不使用其他模型或接口替代。

交互式 CLI 使用原用户环境、`workspace-write` 和 `windows.sandbox=elevated` 的实测未通过：沙箱初始化完成后，`doctor` 在 app-server 的 `thread/read` 步骤收到错误码 `-32600`，原因为 `thread not loaded`，尚未发起模型检测。同一会话在沙箱外可以读取，因此已确认受限执行路径存在限制，底层状态访问失败的具体原因尚未完全确定。上述隔离沙箱通过结果不能替代普通受限配置的验收。

日常使用 Windows 桌面端或 CLI 时，受限会话可通过客户端正常审批，仅允许本条检测／诊断命令在沙箱外运行，无需将整个会话切换为完全访问。Skill 会在已知受限配置下执行前申请；拒绝授权则停止。权限弹窗批准的是该命令在沙箱外执行，不表示受限沙箱本身已兼容。已知能在沙箱内运行的专门配置及用户明确要求的沙箱测试保留原权限。离线报告复查不需要这项连接权限。

## 命令与参数

日常使用优先参考上面的聊天示例。以下为对应的底层命令，在仓库根目录执行；在已安装 Skill 中调用时，将 `scripts/check.mjs` 换为安装目录内的绝对路径。真实检测和连接诊断应在目标 Codex 聊天的执行环境中运行，普通系统终端通常没有当前任务标识。

```sh
node scripts/check.mjs --help
node scripts/check.mjs doctor
node scripts/check.mjs --timeout 300
node scripts/check.mjs --json
node scripts/check.mjs --input "<历史报告.json>" --text
node scripts/check.mjs --output "<报告目录>"
node scripts/check.mjs --input "<历史报告.json>"
node scripts/check.mjs doctor --codex "<Codex可执行文件绝对路径>"
```

| 参数 | 行为 |
| --- | --- |
| 无参数或 `check` | 发起一轮检测，共三条数字挑战 |
| `doctor` | 校验本地 SDK、参考库和当前任务连接，不创建采样会话或请求模型 |
| `--timeout` | 三条采样共享的等待时限，默认 180 秒，范围 5–600 秒；不含连接与会话准备时间 |
| `--json` | 将结果以 JSON 输出，进度仍写入标准错误流 |
| `--text` | 使用含前五名的文字结果，不生成卡片；可配合 `--input` 离线展示 |
| `--output` | 指定报告目录，每次创建新文件，不覆盖已有报告 |
| `--input` | 离线重评分历史报告，要求 SDK 版本和检测器哈希与当前一致 |
| `--codex` | 显式指定当前客户端配套运行时的绝对路径 |
| `--thread` | 诊断用的可信当前任务 ID，通常无需手动提供 |

`--input` 不能与 `doctor`、`--thread`、`--codex` 或 `--output` 组合；`--json` 和 `--text` 不能同时使用。离线复查不连接 Codex，也不发起新探针。

退出码：`0` 表示诊断成功或得到完整／部分排名；`1` 表示输入错误、执行失败、报告保存失败或无法评分；`130` 表示取消，包括连接和会话准备阶段。部分排名仍返回 `0`，判断样本是否充足应同时查看报告。

## 常见问题

| 现象 | 处理方式 |
| --- | --- |
| Skill 未显示 | 在下一轮消息中调用；仍未显示时重新打开 Codex，确认安装目录正确 |
| `NO_CURRENT_THREAD` | 回到目标 Codex 聊天内调用，不从系统终端猜测任务 |
| `CODEX_NOT_FOUND` | 用 `--codex` 指定当前客户端配套运行时；CLI 用户可检查 Codex 安装及 PATH |
| `PERMISSION_DENIED` | 系统拒绝启动 Codex 子进程；Windows 受限会话可仅批准本条命令在沙箱外运行，拒绝则停止 |
| `SPAWN_FAILED` | 核对当前 Codex 可执行文件及运行环境 |
| `THREAD_NOT_FOUND` | 包括 `thread not loaded`；核对运行时、`CODEX_HOME` 及沙箱状态访问权限，不能仅凭此错误断言会话不存在 |
| `MISSING_EFFORT`、`PROTOCOL_ERROR` | 运行时可能缺少所需接口或字段；保留错误并核对客户端版本 |
| `AUTH_REQUIRED` | 在 Codex 中恢复原有登录或渠道认证后，再由用户决定是否检测 |
| `RATE_LIMITED`、`QUOTA_EXHAUSTED` | 检查当前渠道限流或额度，失败不构成模型判断 |
| `PROBE_TIMEOUT` | 本轮未及时完成；需要时显式增加等待时间后重新检测 |
| `ASSET_INTEGRITY` | SDK 或数据与来源记录不符，重新安装完整 Skill，不直接修改哈希绕过检查 |
| `OUTPUT_UNAVAILABLE` | 报告目录不可写或路径无效，修正目录后再检测；本次尚未发起模型测试请求 |
| `REPORT_SAVE_FAILED` | 保存失败但结果仍在输出中，保留完整 JSON，无需重新检测 |
| 目标目录已经存在 | 安装器不覆盖；备份并移出旧 Skill 目录后重新安装 |

Windows 的 `--codex` 指向 `codex.exe` 或 `@openai/codex/bin/codex.js`，不执行 `.cmd`／`.bat` 包装器。多个桌面运行时无法确定时，需要显式指定当前版本。

环境变量 `CODEX_LM_DETECTOR_CODEX_PATH` 等价于默认的 `--codex`；`CODEX_LM_DETECTOR_HOME` 可指定记录根目录，报告保存到其 `reports/` 子目录。`--output` 直接指定报告目录。普通使用无需设置这些变量。

## 报告与隐私

桌面端在一张卡片中显示结论、所选模型、第一候选、前五名排名、有效样本数和 Token 用量，完整报告链接保留在卡片下方。卡片使用随包模板和本次报告生成，不依赖图片渲染、浏览器或额外运行依赖。渠道、参考库时间和 SDK 版本保存在完整报告中。

卡片保存在 `CODEX_HOME/visualizations/YYYY/MM/DD/<当前任务ID>/`，未设置 `CODEX_HOME` 时使用 `~/.codex`。每次生成新文件，不覆盖历史卡片；内容仅包含展示用的结果摘要，不复制原始挑战和回答。

CLI、缺少可信当前任务标识或卡片生成失败时，保留含前五名的文字结果。客户端不支持卡片时，可用 `--input "<报告绝对路径>" --text` 离线查看；`--json` 保持原有格式，不生成卡片。清理报告时如需清除卡片，应另行删除对应卡片文件。

主图标和标题只表示本次检测的完成情况，共五种状态：

| 图标与颜色 | 标题 | 含义 |
| --- | --- | --- |
| 蓝色图表 | 检测完成 · 已生成候选排名 | 三条有效样本，已得到完整排名；未校准时仍注明概率缺失原因 |
| 橙色虚线圆圈 | 已生成部分样本排名 | 有部分有效样本和候选排名，概率需要三条有效样本 |
| 橙色信息 | 本次无法生成有效排名 | 回答不满足评分要求，或检测期间配置变化 |
| 红色感叹号 | 检测未完成 | 连接、认证、限流、超时等导致流程未完成且没有可展示的排名 |
| 灰色停止 | 检测已取消 | 用户主动停止 |

候选一致、不同或所选型号未单独收录放在说明中，不决定主状态。“检测完成”只表示得到了完整排名，不表示确认模型身份。只按上游评分组织展示，不添加匹配阈值。三条样本完整且上游返回校准排名时，已收录和未收录型号均可展示库内相对概率；上游的身份判断证据不足标记不会使该概率失效。样本不全时不作匹配判断；失败、取消或配置变化时不展示残留排名。非零且小于 0.1% 的概率显示为 `<0.1%`，接近 100% 时显示为 `>99.9%`，原始数值不变。

检测前会检查报告目录。若检测完成后仍遇到写入失败，文字输出会保留结果及完整 JSON，不生成报告链接或卡片；将 JSON 代码块保存为 `.json` 文件后，可通过 `--input` 离线复查。`--json` 模式仍返回结构化结果，`saveError` 说明保存失败，`report` 字段保留完整报告。写入失败返回退出码 `1`，不会自动重新检测。

有排名但没有概率时，概率栏显示具体原因，如“有效样本不足（2/3）”或“上游未提供校准概率”。部分样本仍能生成候选排名，概率需要三条有效样本；请求成功返回不一定代表回答满足评分要求。

常见排名可以这样理解，卡片截图直接展示在[仓库 README](https://github.com/logan0817/codex-lm-detector#结果示例)中：

| 示例 | 解读 |
| --- | --- |
| 第一候选与所选型号一致，概率 99.1% | 数字指纹接近，但不是 99.1% 的身份认证准确率 |
| 第一候选 40.1%，第二候选 29.4%，所选型号排第三 | 候选之间的概率较分散，只说明本次回答的相对接近程度，不能认定换模 |
| 型号未单独收录，近似候选概率 >99.9% | 只能比较参考库中的候选，无法据此确认未收录型号的身份 |
| 只有 2/3 条有效样本 | 部分样本仍能生成排名；上游未计算概率，离线复查不能补出缺失样本 |

卡片只列前五名，未列出的候选和数值取整都可能使表格中的百分比合计不等于 100%。

默认报告目录：

| 系统 | 目录 |
| --- | --- |
| macOS | `~/Library/Application Support/codex-lm-detector/reports/` |
| Windows | `%LOCALAPPDATA%\codex-lm-detector\reports\`；缺失时使用用户目录的 `AppData\Local` |
| Linux | `$XDG_STATE_HOME/codex-lm-detector/reports/`；缺失时使用 `~/.local/state/codex-lm-detector/reports/` |

旧版 `lm-detector` 目录内的报告保持原位，可以通过 `--input` 加绝对路径复查；旧环境变量 `LM_DETECTOR_HOME` 和 `LM_DETECTOR_CODEX_PATH` 继续兼容，同名用途的新变量优先。

报告包含挑战、原始数字回答、模型标签、渠道名称、推理档位、客户端来源、Token 用量、候选排名和引擎版本。不包含 API Key、父聊天内容、父任务 ID、工作目录或完整服务端错误。渠道名称可能是内部标签，分享报告前请检查。

评分在本地进行，不向检测网站上传报告。模型采样通过现有 Codex 渠道联网，使用相应账号或渠道额度。报告可以被本地修改，离线重评分不能证明回答的网络来源。

更新或卸载 Skill 不影响独立保存的报告；若需清理历史，另行删除报告目录。

## 实现与参考库

检测流程：读取当前任务配置 → 生成三条上游挑战 → 创建三个无历史临时会话 → 原生采样 → 复查配置 → 本地评分并保存报告。

临时会话核对模型、渠道、工作目录和推理档位，关闭自动模型回退。工具调用、授权请求、失败轮次、超时或取消会使相应样本无效；采样前后配置变化时不作匹配判断。脚本不额外重试，Codex 运行时自身可能重试网络请求。

临时会话不复制父聊天历史，无法保证复现父聊天的任务提示、缓存、服务等级或服务端路由。推理档位为空时沿用原生运行时默认设置。

SDK 的挑战生成和评分逻辑未修改。运行前检查 SDK、参考库和检测器的 SHA-256，并由 SDK 检查数据与检测器兼容性。运行时不自动下载或更新。型号精确收录情况由脚本检查，不推断模型别名。

## 开发与维护

仓库根目录即 Skill：`SKILL.md` 为调用指令，`scripts/` 为检测与展示实现，`agents/` 为界面元数据，`assets/result-card.html` 为卡片模板，`vendor/` 为固定上游组件，`tests/` 为本地测试。

```sh
npm test
```

测试使用 Node.js 内置测试器、随包 SDK 和模拟协议，不消耗模型额度，无需 `npm install`。格式遵循根目录 `.editorconfig` 和现有代码风格。

参与 SHA-256 校验的上游文件通过 `.gitattributes` 禁用 Git 文本转换，保持原始字节，避免 Windows 的 `core.autocrlf` 改写换行后导致 `ASSET_INTEGRITY`。不要修改摘要或跳过校验来解决此错误。

手动安装支持 `node install.mjs --target "<绝对路径>"`，用于测试或自定义安装。只复制 `SKILL.md`、`agents/`、`assets/`、`scripts/`、`vendor/`、`references/` 和许可声明，不复制 Git 元数据及开发文件。

修改 `assets/result-card.html` 后，使用历史报告验证桌面卡片与文字回退结果，同时检查窄屏和明暗主题。README 的结果截图位于 `assets/examples/`，展示发生变化时同步更新。不要修改真实报告以迎合展示结果。

Skill 名、仓库名和默认安装目录均为 `codex-lm-detector`。系统 skill-installer 安装仓库根目录时，内部使用 `--path . --name codex-lm-detector`；用户只需发送 README 中的安装语句，无需手动填写参数。本项目不修改系统安装器。

本项目独立维护 Codex 接入和采样实现。更新 lm-detector 组件时，替换完整匹配的 SDK 与数据，同时更新 `vendor/provenance.json` 中的版本、来源和摘要，以及本页版本信息。保留 lm-detector 组件许可，运行本地测试，并核对与直接调用 SDK 的评分一致性。不要单独替换参考库或绕过完整性检查。旧报告需要保留原版本引擎才能复查。

组件版本和许可见 [lm-detector 组件说明](../THIRD_PARTY_NOTICES.md)，文件摘要见 [vendor/provenance.json](../vendor/provenance.json)。
